2) What Was Implemented
- A typed `apiFetch<T>` client in `lib/api.ts` that joins `VITE_API_BASE_URL`,
  injects `Authorization: Bearer <token>` when a token is supplied, sets JSON
  headers, parses JSON responses, and throws an `ApiError(status, detail)` that
  unwraps FastAPI's `{detail}` and validation-error array shapes. Network
  failures surface as `ApiError(0, "Network request failed")` so the UI can
  distinguish them from server rejections.
- A pure `decodeJwtPayload(token)` helper that base64-url decodes the middle
  JWT segment with TextDecoder/UTF-8 safety. Used to read non-secret claims
  (`sub`, `exp`) for client-side session bookkeeping; the server still
  validates every request via `get_current_user` (SEC-01), so this is purely a
  UX convenience.
- `auth-api.ts` exports `loginRequest({ email, password })` calling
  `POST /auth/login` and typed against the backend `TokenResponse`
  (`access_token`, `token_type: "bearer"`, `expires_in`, `role`).
- `AuthProvider` now stores a richer `AuthSession` with `expiresAt` (epoch ms,
  derived from the JWT's `exp` claim, falling back to `Date.now() + expires_in
  * 1000`) and exposes an async `signIn(email, password)` method on the
  context. On successful login the provider builds the session, persists it
  to localStorage, and starts a `setTimeout` that auto-clears the session a
  few seconds before the token expires so route guards can react.
- A 5-second `EXPIRY_GRACE_MS` keeps the UI from sending requests with a
  token that the server is about to reject for clock skew.
- `ProtectedRoute` now distinguishes "no session" (`reason=required`) from
  "session expired here" (`reason=expired`) and forwards both as a query
  string to `/login`, while preserving the originally requested path in
  `location.state.from` for post-login redirect.
- `LoginPage` is now a proper form: email + password fields with
  `autoComplete="username" / current-password"`, native required validation,
  disabled state during submission, and a single submit button that switches
  to "Signing in..." while the request is in-flight.
- Error handling maps the SEC-01 contract to user-friendly copy:
  - 401 -> "Invalid email or password."
  - 503 -> "Authentication service is unavailable. Try again shortly."
  -   0 -> "Could not reach the server. Check your connection."
  - other -> server-provided detail or generic fallback.
- Reason-aware notice: when redirected here from a protected route, the page
  shows "Your session expired" / "Please sign in to continue" until the user
  starts typing or an error replaces it.
- Successful login redirects the user back to `location.state.from` (the URL
  they originally tried to load) or `/dashboard` by default.

3) Acceptance Checklist
- [x] Login form posts to `/api/v1/auth/login` with the JSON shape the SEC-01
      schema expects (email + password).
- [x] Bearer token from `TokenResponse.access_token` is stored in
      `AuthContext` and persisted to localStorage; subsequent reloads keep
      the user signed in until expiry.
- [x] `expires_in` (and the JWT `exp` claim) drives an automatic sign-out so
      stale tokens never leave the client; ProtectedRoute then redirects to
      `/login?reason=expired`.
- [x] Invalid credentials show the error inline without leaving the page.
- [x] Form is keyboard-accessible: explicit `<label htmlFor>` pairs, focus
      ring via global `:focus-visible`, `role="alert"` on the error region,
      `role="status"` on the redirect notice.
- [x] Post-login navigation honors the original requested path saved by
      `ProtectedRoute` in `location.state.from`.
- [x] Sign-out (TopBar) clears the localStorage entry; route guards then
      redirect any subsequent navigation to /login.
